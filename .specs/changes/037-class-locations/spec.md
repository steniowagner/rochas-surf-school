# 037 — Class locations: map point, address suggestions, editing and removing

## Goal

Locations become what requirements 3.2 asks for. Admins save a location with a point on a map, helped by address
suggestions from Google Maps Platform. They edit a saved location, and the change applies to every class that uses
it, past ones included; when upcoming classes use it, they choose whether to tell those classes' instructors. They
"remove" a location, which archives it: it is no longer offered for new classes, and the classes that used it keep
showing it. Everyone sees the location on a small map on the class details, with a "Direções" button that opens the
phone's maps app. Spec 028 built only a name and an address; this spec completes locations, except for students,
who will be told about location changes once enrolment exists.

## Scope

### In scope

- A location's map point (latitude and longitude), required when a location is created or edited; the 028
  locations keep working without one until they are edited.
- Editing a location (name, address, point) by approved admins, applied to every class that uses it; the
  deadlines of its upcoming classes cleared when its name or address changes; the optional `location.changed`
  notification to the instructors of its upcoming classes.
- Removing a location: it is archived, leaves the list, frees its name, and can't be picked for a class; the
  classes that use it keep it.
- Address suggestions and the place behind a suggestion, through the backend, from Google Places API (New).
- The location's point in every class read (`ClassItem`).
- Mobile: `react-native-maps` (with its Expo config plugin and an `app.config.ts`); the "Novo local" / "Editar
  local" sheet with the address search, its suggestions and the map point; the "Gerir" / "Concluir" mode of the
  location list on Nova aula and Editar aula; the "Remover local" confirmation; the map and "Direções" on the
  class details; a tap on a `location.changed` push.
- Web: the privacy policy names Google's address suggestions and Apple Maps, in pt-BR, es and en.
- Copy in pt-BR, es-ES and en-US.

### Out of scope

- Telling students and people with pending requests about a location change (with enrolment).
- Restoring an archived location, listing archived locations, and a locations screen outside the class form.
- Weather and sea conditions on the class details, and the design's "Avisar alunos e instrutores" class tool.
- Reverse geocoding (an address from a tapped point), the phone's own location ("near me"), and an interactive
  map on the class details (it is a fixed preview).
- Recomputing deadlines when only the point moves (the model doesn't read the point, D-08).
- Google Maps on iOS: iOS uses Apple Maps (D-03).
- "My classes", the demote and remove triggers of the "no instructor" flag, and every other follow-up.

## Decisions

| ID   | Decision | Reason |
| ---- | -------- | ------ |
| D-01 | A location gains `latitude` (−90 to 90) and `longitude` (−180 to 180), numbers, nullable in the database. `POST /locations` and `PUT /locations/:id` require both: missing (either one absent or `null`) → `location.point.required`; present but not a finite number or out of range → `location.point.invalid`; collected with the name and address keys into one 422. Existing locations without a point keep working: they can be picked for classes, and they show no map. | A point is what the map and "Direções" need; forcing it on old rows would block their classes. |
| D-02 | Address suggestions come from the backend, which calls **Google Places API (New)** behind an `AddressSuggestionProvider` port in `modules/classes` (`suggest({ query, sessionToken, language })` → `{ placeId, title, description }[]`, at most 5; `findPlace({ placeId, sessionToken, language })` → `{ address, latitude, longitude, name }` or `null`), implemented by `GooglePlacesAddressSuggestionProvider` (`apps/backend/src/modules/classes/google-places.address-suggestions.ts`): `POST https://places.googleapis.com/v1/places:autocomplete` with a location bias (a circle of 50 km around Fortaleza, −3.7319, −38.5267) and `GET https://places.googleapis.com/v1/places/{placeId}` with the field mask `formattedAddress,location,displayName`, both with the `X-Goog-Api-Key` header, the `sessionToken` and `languageCode`. Variable: `GOOGLE_MAPS_API_KEY` (backend). Without it outside production the provider answers no suggestions and no place (logged once); in production the backend refuses to start without it. | The key stays on the server, the provider is swappable and faked in tests, and the same rule as Resend and Anthropic applies to a missing key. |
| D-03 | The phone draws maps with **`react-native-maps`** (installed with `npx expo install`): Apple Maps on iOS (no key), Google Maps on Android (`PROVIDER_GOOGLE`), with the `react-native-maps` config plugin's `androidGoogleMapsApiKey`. The key comes from `GOOGLE_MAPS_ANDROID_API_KEY` in `apps/mobile/.env`, read by a new `apps/mobile/app.config.ts` that takes the `app.json` config Expo passes in and appends the plugin entry (so `app.json` stays the source of everything else). Jest mocks `react-native-maps` in `jest.setup.ts` (`MapView` and `Marker` as host views that keep their props). | The technical context already names `react-native-maps`; Apple Maps needs no key and no billing; a native folder is never edited by hand. |
| D-04 | Routes, all protected. `GET /locations` (any approved account) → 200 `{ items: [{ id, name, address, latitude, longitude, upcomingClasses }] }`: only **active** locations, sorted by `nameKey` then `id`; `latitude` / `longitude` are `null` when not set; `upcomingClasses` counts the classes at that location that start after now and aren't cancelled. `POST /locations` (admins) `{ name, address, latitude, longitude }` → 201 with the same item shape (`upcomingClasses` 0). `PUT /locations/:id` (admins) `{ name, address, latitude, longitude, notify? }` → 200 with the item. `POST /locations/:id/archive` (admins) → 204. `GET /locations/address-suggestions?q=&sessionToken=&language=` (admins) → 200 `{ items: [{ placeId, title, description }] }`. `GET /locations/address-suggestions/:placeId?sessionToken=&language=` (admins) → 200 `{ address, latitude, longitude, name }`. | One resource for everything about locations, the same access rule as creating one (D-10 of 028). |
| D-05 | Editing a location, in this order: access (`user.status.notApproved`, then `user.role.notAdmin`); the id (not a UUID, or no location → 404 `location.notFound`); the shape, every problem together (422): `location.name.*`, `location.address.*`, `location.point.*`, and `location.notify.invalid` when `notify` is present and not a boolean; then `location.archived` (409, an archived location can't be edited); then `location.name.duplicate` (409, another **active** location has the same `nameKey`; its own name in another case or with other accents is fine). A save where name, address, latitude and longitude are all the same as stored (after trimming) is answered 200 with the location, writes nothing and tells nobody. | The same order as editing a class: who, which, what, then the stored state. |
| D-06 | Archiving sets `archived_at` and sets `name_key` to `NULL` in the same write, so the unique index on `name_key` (kept as it is; Postgres treats NULLs as distinct) only binds active locations: a new or renamed location may take an archived one's name. Order: access; the id (404 `location.notFound`); `location.archived` (409, already archived). The write is conditional on `archived_at IS NULL`, so of two concurrent archives one wins and the other gets `location.archived`. Archived locations are never listed and can't be edited. | Freeing the name lets an admin add a place again after removing it, with no restore flow; a nullable key avoids a partial index Prisma may not model. |
| D-07 | The design's rule "Tem de existir pelo menos um local" is not kept: the last active location can be removed. | "Novo local" is always offered on the class form, so an empty list is never a dead end. |
| D-08 | When an edit changes the **name or the address**, the same write clears the cancellation deadline (and bumps the deadline revision, as the rule save does) of every class at that location that starts after now and isn't cancelled; the deadline job (spec 036) works them out again. A change of the point only doesn't clear them, and past, started and cancelled classes keep theirs. | The model reads the location's name and address (spec 036), never the point; a stale deadline must not survive a detail it was computed from. |
| D-09 | With `notify: true` and a change to the name, the address or the point, after the write, every instructor of the location's upcoming classes (start after now, not cancelled) except the admin who edits gets **one** `location.changed` notification with `{ count, locationName }` (`count` = that instructor's upcoming classes at the location, `locationName` = the new name), through a `LocationChangeNotifier` port (`locationChanged({ recipients: [{ instructorId, count }], locationName })`) implemented by `NotificationsLocationChangeNotifier`, which logs and swallows every error. `notify` absent or `false`, no upcoming class, or an unchanged save → nobody is told. A failed notification never changes the 200. | Requirements → Notifying about a location change; one notification per person, like `class.assigned`; the editor knows already. |
| D-10 | An archived location can't be given to a class: `POST /classes/batch` with an archived `locationId` → 422 `class.location.archived` (checked right after `class.location.notFound`); `PUT /classes/:id` that changes the location to an archived one → the same 422 (after `class.location.notFound`). An edit that keeps a class's current location is accepted even when that location is archived. | Requirements → Archiving instead of deleting: no longer offered for new classes, while existing classes keep it. |
| D-11 | Only instructors can be told about a location change: students and pending requests come with enrolment. The checkbox reads "Avisar os instrutores das próximas aulas?". | No enrolment exists yet (same as specs 032–034). |
| D-12 | `ClassItem.location` (week list and one class) gains `latitude` and `longitude` (`null` when the location has none). Archived locations are read the same way as active ones. | The details' map needs the point; history keeps showing the place. |
| D-13 | Address suggestion queries: `q` trimmed, 3 to 100 characters, else 422 `location.suggestions.query.invalid`; `sessionToken` required, 1 to 64 characters of `[A-Za-z0-9_-]`, else 422 `location.suggestions.sessionToken.invalid`; `language` one of `pt-BR`, `es`, `en` (else `pt-BR`). The provider failing (non-2xx, network) → 502 `location.suggestions.unavailable`; an unknown place → 404 `location.place.notFound`. The app sends a new `sessionToken` (a UUID v4) each time the sheet opens, the app's backend locale as `language`, and asks for suggestions 300 ms after the last keystroke once the address has 3 characters or more. | Google bills autocomplete by session; validating the inputs keeps junk off the paid API. |
| D-14 | In the app, the location sheet ("Novo local" / "Editar local") has: Nome (`TextInput`, max 40, the inline duplicate message against the loaded active list ignoring the location being edited); Endereço (`TextInput` with a search icon, max 200) with up to 5 suggestion rows under it (title and description) while it is focused and has suggestions; picking one sets the address to the place's `address`, moves the point to the place's, fills Nome with the place's `name` only when Nome is empty, and hides the rows; failures of the suggestions show no toast and no rows (the admin can still type and tap the map); "Ponto no mapa": a `MapView` 170 pt tall, rounded, opened on the point (or on Fortaleza, −3.7319, −38.5267, with a 0.2° span, when there is none), a `Marker` on the point, a tap anywhere setting the point, and the hint "Toque no mapa para marcar o ponto" / "Toque para mover o ponto"; the notify `Checkbox` only when editing and `upcomingClasses` > 0, on by default; the primary button ("Salvar local" when creating, "Salvar" when editing) enabled only with a name, an address, a point and no duplicate; "Remover local" (outline, editing only); "Cancelar". The sheet sets `contentPanningEnabled={false}` so the map takes drags. | AULAS-03A's sheet adapted to Brazilian Portuguese and to D-07 / D-11. |
| D-15 | The "Local" section of Nova aula and Editar aula shows "Gerir" on the right of its title while at least one active location exists; in that mode it reads "Concluir", each row shows a pencil instead of the check and opens "Editar local" for that row, and "Novo local" is hidden. Saving an edit updates the cached list (the row's name, address and point) and keeps the selection. "Remover local" opens a confirmation sheet ("Remover local?", the name, the address, "Ele deixa de aparecer para novas aulas." plus, when `upcomingClasses` > 0, "As N aulas que já usam este local continuam como estão.", "Remover local" danger and "Manter"); on 204 the location leaves the cached list, the edit sheet closes, the toast "<nome> removido" shows, and, when it was the form's selection, the selection is cleared (so the submit button disables until another is picked). On Editar aula, a class whose current location isn't in the active list shows that location as its selected row, with the chip "Removido", and can keep it. | Requirements → Removing the selected location while creating classes; the design's "Gerir" mode. |
| D-16 | Error mapping in the app: `location.name.duplicate` (409) → the inline duplicate message and the locations refetched (as today); `location.archived` and `location.notFound` on an edit or a removal → toast `locationSheet.errors.gone`, the locations refetched and the sheet closed; `class.location.archived` on submit (Nova aula or Editar aula) → toast `newClass.errors.locationArchived`, the locations refetched and the selection cleared; `NetworkError` → no connection; `SessionExpiredError` → nothing; anything else → generic. | One mapping per route, as the technical context requires. |
| D-17 | On the class details, the location card shows, when the location has a point, a non-interactive `MapView` 96 pt tall (scroll, zoom, rotate and pitch off) centered on the point with a `Marker`, and a "Direções" button that opens `https://maps.apple.com/?daddr=<lat>,<lng>` on iOS and `https://www.google.com/maps/dir/?api=1&destination=<lat>,<lng>` on Android with `Linking.openURL` (toast `classDetails.directionsUnavailable` when it fails). Without a point: the name and the address only, as today. Every role sees it. | AULAS-02's `dMapaLocal`; both URLs open the native maps app or the browser without another library. |
| D-18 | A tap on a `location.changed` push opens the classes tab of an instructor or an admin (`routes.instructor.classes` / `routes.admin.classes`), like `class.assigned`; a `location.changed` push received with the app open invalidates `["classes"]` and `["locations"]`. | The push concerns several classes, not one. |
| D-19 | Structure: the location use cases `EditLocation`, `ArchiveLocation`, `SuggestAddresses` and `FindAddressPlace` live in `modules/classes/src/location/usecase/`; the ports `LocationChangeNotifier` and `AddressSuggestionProvider` in `modules/classes/src/location/provider/`. `LocationRepository` gains `findActive()` (with the upcoming counts as of a given now), `update(location, { clearDeadlinesFrom: Date \| null })`, `archive(id)` (conditional) and `findUpcomingInstructorCounts(locationId, now)`. In the app, the map pieces are components in `apps/mobile/src/modules/classes/components/` (`location-map-picker`, `location-map-preview`, `address-search-field`, `archive-location-sheet`). | Locations stay one aggregate; the classes read through the existing view reader. |

## Expected Results

### ER-01 — A new location needs a point on the map

- **Front:** backend
- **Behavior:** Given an approved admin, when they call `POST /locations` with `{ name: "Praia do Futuro",
  address: "Av. Zezé Diogo, 5000 – Fortaleza", latitude: -3.7442, longitude: -38.4617 }`, then the API answers 201
  `{ id, name, address, latitude: -3.7442, longitude: -38.4617, upcomingClasses: 0 }`, and `GET /locations` lists it
  with its point and `upcomingClasses`.
- **Edge and error cases:** no `latitude` or no `longitude` (or `null`) → 422 `location.point.required`; a string,
  `NaN`, latitude 91 or longitude −181 → 422 `location.point.invalid`; both collected with the name and address keys;
  a location created before this spec answers `latitude: null, longitude: null`; `upcomingClasses` counts only classes
  starting after now that aren't cancelled; nothing is stored on a refusal.
- **Verify by:** `cd apps/backend && npx vitest run --config vitest.config.e2e.ts test/locations.e2e-spec.ts -t "point"`
  and `cd modules/classes && npx jest test/location -t "point"`.

### ER-02 — Admins edit a location and every class follows

- **Front:** backend
- **Behavior:** Given location L used by a finished class and by a class tomorrow, when an approved admin calls
