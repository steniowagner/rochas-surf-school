# 073 — Student app designs page

## Goal

People interested in the app can open `/{lang}/designs/student-app` on the public site and see every screen a
student sees — the agenda, a class with each enrolment status, their classes and history, the school's people, the
profile with its sheets and sub-screens, and the notifications — in every state the app draws, in the theme and
language picked in the site header. `student-app.html` in `.docs/designs` is then generated from that page, in pt-BR
with light and dark side by side, replacing the outdated European Portuguese prototype and its ratings and photos.

## Scope

### In scope

- The `/{lang}/designs/student-app` page with every frame of the inventory, its id and a note, following the
  header's theme and language, and its card on the designs index.
- The web mock components and screen mocks it needs, including a tall phone frame.
- `student-app.html` generated from that page (pt-BR, light and dark side by side) by `build-design.mjs`, with the
  old prototype's sources and photos removed.

### Out of scope

- The instructor and admin variants of the shared screens (class details tools and take-out, people actions, the
  admin's profile, …) and the instructor and admin pages (specs 074 and 075).
- Class ratings, class photos, profile photos and anything else the app doesn't have.
- Frames with the keyboard open, Android frames, clickable prototypes.
- Changing any mobile or backend code or copy.
- Changing what the design system or auth flow pages show.

## Decisions

| ID   | Decision | Reason |
| ---- | -------- | ------ |
| D-01 | The page shows only what a student sees. Screens shared by the three roles (class details, people, profile, notifications) are drawn in their student form; 074 and 075 add their own role's forms on their pages. | The user's choice: one role per page, and each page stays reviewable. |
| D-02 | Screens whose content is longer than the phone are drawn as *tall* frames: `phone-frame` gets a `tall` option, and the frame grows to the whole scrolled content with the mock data, the status bar at the top and the tab bar or footer at the bottom. Sheets and toasts are drawn over phone-height (402 × 874) frames. The inventory marks which frames are tall. | The user's choice: every row is visible, for example the profile's links below the fold. |
| D-03 | Class details get one frame per enrolment status (with the button `getEnrolmentCta` gives it) and one per class state for a class the student isn't in (open, full with the waiting list open or closed, started, finished, cancelled, no instructor, the deadline passed or missing), plus the four enrolment sheets and their states, and loading, not found and error — not every combination of status and class state. | The user's choice: about 30 frames instead of more than 40 that differ only slightly. |
| D-04 | Texts the school types — the denial and take-out reasons, the cancellation rules, the school rules, the class notes — are mock text in the page's language, from the web dictionaries; 072's mock school rules are reused. | As 072 D-04: they aren't app copy, and a reader of any language should understand them. |
| D-05 | The notification rows' titles and bodies are the in-app texts the backend writes (`push-messages.ts`), copied into the web dictionaries for each language with the mock class's values filled in. | The web can't import the backend, and the rows must read as the app shows them. |
| D-06 | `student-app.html`'s sources are generated from `/pt-br/designs/student-app` by `node .docs/designs/scripts/build-design.mjs student-app` and packed with `pack.mjs`; `student-app` joins the generator's slugs, and the old prototype (`App Aluno.dc.html`, its template and the `ph*.jpg` photos) is removed. | Same as 072 D-01: the web page is the single source of truth. |
| D-07 | Mocks of screens shared by roles live in `apps/web/src/modules/designs/screens/shared/` and take what a role changes as props (for class details: the enrolment part, absent for other roles); student-only screens live in `screens/student/`; the page sections are `components/student-app-{agenda,class,my-classes,school,profile,notifications}/`, composed by `pages/student-app/`. Each folder follows `.claude/rules/react.md`. | 074 and 075 add their variants to the same mocks instead of copying them. |

## Expected Results

### ER-01 — student-app.html shows the app's student screens

- **Front:** designs
- **Behavior:** Given `.docs/designs/student-app.html` opened in a browser, then it shows every entry of
  [student-app-inventory.md](student-app-inventory.md) with its id, in pt-BR, each in light and dark side by side,
  matching the web page `/pt-br/designs/student-app`, with the tall frames drawn at their full height.
- **Edge and error cases:** `.docs/designs/src/student-app/App Aluno.dc.html` and the `ph*.jpg` photos no longer
  exist; no European Portuguese wording and no rating or photo screen is left (for example "ecrã", "Já a seguir",
  "As minhas", "Avaliar"); regenerating `design-system` and `auth-flow` changes them only in the compiled CSS (072
  A-01); `pack.mjs --check` exits 0.
- **Verify by:** `node .docs/designs/scripts/pack.mjs --check` exiting 0,
  `test ! -e ".docs/designs/src/student-app/App Aluno.dc.html"`,
  `ls .docs/designs/src/student-app | grep -c "^ph"` printing 0,
  `grep -rliE "ecrã|Já a seguir|As minhas|avaliar" .docs/designs/src/student-app` finding nothing, and opening the
  file in a browser to walk the inventory.

### ER-02 — The designs index lists the student app

- **Front:** web
- **Behavior:** Given `/{lang}/designs` for each of `pt-br`, `es` and `en`, then it shows a card for the student app
  after the auth flow's, with its title and description in that language, linking to `/{lang}/designs/student-app`.
- **Edge and error cases:** `/designs/student-app` without a language redirects with 307 to the browser's language
  (pt-br when none matches); the other cards don't change; no card for the instructor or admin pages.
- **Verify by:** `apps/web/e2e/designs.e2e.ts` → `index lists the design pages in every language` and
  `redirects /designs/student-app to the browser language`, run by `node .specs/scripts/run-e2e.mjs 073`.

### ER-03 — The student app page shows every inventory frame

- **Front:** web
- **Behavior:** Given `/{lang}/designs/student-app`, then for every id in
  [student-app-inventory.md](student-app-inventory.md) an element with `data-design-id="<id>"` is visible, showing
  the entry's title, its note and its iOS phone frame, which matches the app as a student sees it by 071's fidelity
  rule (D-08); entries that list other messages show them in the note; tall frames show their whole content.
- **Edge and error cases:** the six sections are in the inventory's order; the page sets its translated `<title>`
  and description; ST-05-01's frame shows "Remover a conta" below the fold of a phone-height screen, with the tab bar
  at the frame's bottom; no frame shows a rating, a photo or an instructor or admin action.
- **Verify by:** `apps/web/e2e/designs.e2e.ts` → `student app shows every inventory entry` (pt-br, es and en) and
  `student app draws tall frames`, and the reviewer walking the page against the mobile code.

### ER-04 — The student app page follows the page language

- **Front:** web
- **Behavior:** Given `/{lang}/designs/student-app`, then the copy inside the frames is the app's copy in that
  language, the notification rows are the backend's texts in that language (D-05), and the section titles, notes and
  mock texts (D-04) are in that language: for example the ST-02-01 footer button reads "Pedir para entrar" on
  `/pt-br`, the es-ES text on `/es` and the en-US text on `/en`.
- **Edge and error cases:** choosing another language in the header opens the same page in that language;
  interpolated values and plurals (dates, deadlines, counts) are filled, with no `{{…}}` or raw tags on the page.
- **Verify by:** `apps/web/e2e/designs.e2e.ts` → `student app follows the language`.

### ER-05 — The student app page follows the header theme

- **Front:** web
- **Behavior:** Given `/{lang}/designs/student-app`, when the visitor presses the header's theme toggle, then every
  frame switches to the other palette, and the choice is kept on reload.
- **Edge and error cases:** without a stored choice the page follows the OS color scheme.
- **Verify by:** `apps/web/e2e/designs.e2e.ts` → `student app follows the theme toggle` (the computed background of
  the ST-01-01 frame changes between the light and dark `page` token values).

### ER-06 — The student app page fits wide and phone viewports

- **Front:** web
- **Behavior:** Given a 1600 px wide viewport, then the page's content is up to 1440 px wide; given a 375 px wide
  viewport, then `/{lang}/designs/student-app` has no horizontal scroll and the phone frames, tall ones included, are
  scaled down to fit.
- **Edge and error cases:** the existing e2e tests of the site, the design system and the auth flow keep passing.
- **Verify by:** `apps/web/e2e/designs.e2e.ts` → `design pages are wide` and `design pages fit a phone viewport`,
  both covering the student app page.
