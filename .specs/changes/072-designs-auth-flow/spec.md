# 072 — Auth flow designs page

## Goal

People interested in the app can open `/{lang}/designs/auth-flow` on the public site and see every screen a person
goes through before reaching their role's home — signing in, the email and code flow, approval, onboarding, the rules
update and the closed-account screens — in every state the app draws, in the theme and language picked in the site
header. `auth-flow.html` in `.docs/designs` is then generated from that page, in pt-BR with light and dark side by
side, replacing the outdated European Portuguese prototype.

## Context

- Product: [product.md](../../memory/product.md) — relevant concepts: account statuses (pending, approved,
  denied, deleted, removed), onboarding (WhatsApp number, school rules), reactivation requests, the three app
  languages, the public site's designs area (spec 071).
- Requirements: [requirements.md → 6.1 Public web pages](../../../.docs/requirements.md#61-public-web-pages) — the
  designs area this spec adds a page to;
  [1.1 User authentication](../../../.docs/requirements.md#11-user-authentication),
  [1.2 Account lifecycle](../../../.docs/requirements.md#12-account-lifecycle) and
  [1.5 School rules](../../../.docs/requirements.md#15-school-rules) — the screens the page shows, as built;
  [user-journeys.md → header](../../../.docs/user-journeys.md#surf--skate-school-scheduling-platform---user-journeys)
  — its "Designs" line describes how each `.html` is produced, which D-01 changes for `auth-flow.html`.
- Technical: [technical-context.md](../../memory/technical-context.md) — relevant sections: Applications →
  `apps/web` (the `/designs` routes, `src/modules/designs/`, the dictionaries), Automated validation (Vitest and
  Playwright on web), Coverage (`apps/web/src/**` and `.docs/designs/**` are excluded).
- Spec 071 (finished, `.specs/finished/20261028214702-071-designs-foundation-design-system/`) built what this spec
  reuses, and its decisions still apply: iOS frames only (D-03), the app's copy from

  presentational mocks in `apps/web/src/modules/designs/` (D-12), the typed list of design pages and
  `dynamicParams = false` (D-13), the 1440 px design layout (D-15). Its amendment A-01 made the web page the source
  of `design-system.html`, generated by `.docs/designs/scripts/build-design-system.mjs`.
- Web building blocks that already exist in `apps/web/src/modules/designs/components/`: `phone-frame`,
  `design-section`, `design-entry`, `app-icon`, `button`, `text-input`, `text-button`, `otp-input`, `checkbox`,
  `phone-number-field`, `country-picker`, `bottom-modal`, `language-sheet`, `toast`, `stack-header`,
  `screen-intro`, `account-status`, and the mock data in `data/fortaleza.ts` (`people`: Ana Beatriz Lima,
  `ana.lima@email.com`).
- The app screens the page reproduces: `apps/mobile/src/modules/{auth,pending,onboarding,school-rules,rules-update,reactivation,offboarding}/`
  and `apps/mobile/src/components/{account-status,contact-school-button,whatsapp-number-form}/`. The sign-in screen
  always uses the light palette and draws `apps/mobile/assets/images/team-hero.jpg` and `google-logo.svg`.
- Current `auth-flow.html`: sources in `.docs/designs/src/auth-flow/` (`Login Screen.dc.html`, `template.html`,
  `shell.html`, `bundle.json`), an x-dc prototype in European Portuguese with an Apple button, no loading, error or
  toast states, and no Google-name or rules-update screen.
- What the page shows: [auth-flow-inventory.md](auth-flow-inventory.md) — 49 frames in four sections.

## Scope

### In scope

- The `/{lang}/designs/auth-flow` page with every frame of the inventory, its id and a note, following the header's
  theme and language, and its card on the designs index.
- The web mock components and screen mocks it needs, and the sign-in photo and Google logo copied into the web's
  designs module.
- `auth-flow.html` generated from that page (pt-BR, light and dark side by side) by a generator generalized from
  `build-design-system.mjs`, with the old prototype's sources removed.

### Out of scope

- The student, instructor and admin designs (specs 073–075).
- The Apple button and anything else the app doesn't have.
- Frames with the keyboard open, Android frames, clickable prototypes.
- Changing any mobile screen, component or copy.
- Changing what the design system page or `design-system.html` show.

## Decisions

| ID   | Decision | Reason |
| ---- | -------- | ------ |
| D-01 | The web page is the source of truth: `auth-flow.html`'s sources (`.docs/designs/src/auth-flow/`) are generated from `/pt-br/designs/auth-flow` and packed with `pack.mjs`, as spec 071's A-01 did for the design system. `build-design-system.mjs` becomes `.docs/designs/scripts/build-design.mjs <slug>` (`design-system` or `auth-flow`), and running it for `design-system` gives the same sources as before. | The user's choice: hand-editing the x-dc prototype duplicates the React work and drifts from it. |
| D-02 | One frame per visual state. Messages that differ only in their text (toasts, inline errors) appear once in a frame; the entry's note lists the screen's other messages with the app's copy in the page's language. | The user's choice: every message is covered without about 20 frames identical apart from the text. |
| D-03 | The sign-in frames draw the app's own `team-hero.jpg` and `google-logo.svg`, copied into `apps/web/src/modules/designs/assets/`; the generated `.html` embeds them as assets. | The user's choice: the frame looks like the app. |
| D-04 | The admin's denial reason (AF-04-05, AF-04-07) is mock text in the page's language, from the web dictionaries; the rest of the mock account comes from `people` in `data/fortaleza.ts`, and the school rules shown are mock rules in the page's language, also from the dictionaries. | The reason and the rules are typed by the school, not app copy, so a reader of any language should understand them. |
| D-05 | Whole-screen mocks live in `apps/web/src/modules/designs/screens/auth/` (one `*-screen` folder per screen), take their state as props and stay presentational; the page sections are `components/auth-flow-{sign-in,email,onboarding,closed-account}/`, composed by `pages/auth-flow/`. Each folder follows `.claude/rules/react.md`. | Same structure as spec 071's design system page; the next specs reuse the screens folder. |
| D-06 | The sign-in frames stay in the light palette in both themes; every other frame follows the header's theme. | The app's sign-in screen always uses the light palette (fidelity rule, 071 D-08). |

## Expected Results

### ER-01 — auth-flow.html shows the app's auth flow

- **Front:** designs
- **Behavior:** Given `.docs/designs/auth-flow.html` opened in a browser, then it shows every entry of
  [auth-flow-inventory.md](auth-flow-inventory.md) with its id, in pt-BR, each in light and dark side by side,
  matching the web page `/pt-br/designs/auth-flow`; the sign-in frames show the team photo and the Google logo.
- **Edge and error cases:** `.docs/designs/src/auth-flow/Login Screen.dc.html` no longer exists; no European
  Portuguese wording is left (for example "registo", "ecrã", "Iniciar sessão"); no Apple button; running
  `build-design.mjs design-system` leaves `.docs/designs/src/design-system/` unchanged; `pack.mjs --check` exits 0.
- **Verify by:** `node .docs/designs/scripts/pack.mjs --check` exiting 0,
  `test ! -e ".docs/designs/src/auth-flow/Login Screen.dc.html"`,
  `grep -rlE "registo|ecrã|Iniciar sessão|com a Apple" .docs/designs/src/auth-flow` finding nothing, and opening the file
  in a browser to walk the inventory.

### ER-02 — The designs index lists the auth flow

- **Front:** web
- **Behavior:** Given `/{lang}/designs` for each of `pt-br`, `es` and `en`, then it shows a card for the auth flow
  after the design system's, with its title and description in that language, linking to `/{lang}/designs/auth-flow`.
- **Edge and error cases:** `/designs/auth-flow` without a language redirects with 307 to the browser's language
  (pt-br when none matches); the design system card doesn't change; no card for the student, instructor or admin
  pages.
- **Verify by:** `apps/web/e2e/designs.e2e.ts` → `index lists the design pages in every language` and
  `redirects /designs/auth-flow to the browser language`, run by `node .specs/scripts/run-e2e.mjs 072`.

### ER-03 — The auth flow page shows every inventory frame

- **Front:** web
- **Behavior:** Given `/{lang}/designs/auth-flow`, then for every id in
  [auth-flow-inventory.md](auth-flow-inventory.md) an element with `data-design-id="<id>"` is visible, showing the
  entry's title, its note and its iOS phone frame, which matches the app by 071's fidelity rule (D-08); entries that
  list other messages (D-02) show them in the note.
- **Edge and error cases:** the four sections are in the inventory's order; the page sets its translated `<title>`
  and description; no frame shows the Apple button.
- **Verify by:** `apps/web/e2e/designs.e2e.ts` → `auth flow shows every inventory entry` (pt-br, es and en), and the
  reviewer walking the page against the mobile code.

### ER-04 — The auth flow page follows the page language

- **Front:** web
- **Behavior:** Given `/{lang}/designs/auth-flow`, then the copy inside the frames is the app's copy in that
  language and the section titles, notes and mock texts (D-04) are in that language: for example the AF-01-01 Google
  button reads "Continuar com o Google" on `/pt-br` and "Continue with Google" on `/en`, with the es-ES text on `/es`.
- **Edge and error cases:** choosing another language in the header opens the same page in that language;
  interpolated values (email, first name, countdown) are filled, with no `{{…}}` or raw tags on the page.
- **Verify by:** `apps/web/e2e/designs.e2e.ts` → `auth flow follows the language`.

### ER-05 — The auth flow page follows the header theme

- **Front:** web
- **Behavior:** Given `/{lang}/designs/auth-flow`, when the visitor presses the header's theme toggle, then every
  frame except the sign-in ones switches to the other palette, and the choice is kept on reload.
- **Edge and error cases:** the sign-in frames (AF-01-01 to AF-01-05) keep the light palette in both themes (D-06);
  without a stored choice the page follows the OS color scheme.
- **Verify by:** `apps/web/e2e/designs.e2e.ts` → `auth flow follows the theme toggle` (the computed background of
  the AF-02-01 frame changes between the light and dark `page` token values, and AF-01-01's stays light).

### ER-06 — The auth flow page fits wide and phone viewports

- **Front:** web
- **Behavior:** Given a 1600 px wide viewport, then the page's content is up to 1440 px wide; given a 375 px wide
  viewport, then `/{lang}/designs/auth-flow` has no horizontal scroll and the phone frames are scaled down to fit.
- **Edge and error cases:** the existing e2e tests of the site and the design system keep passing.
- **Verify by:** `apps/web/e2e/designs.e2e.ts` → `design pages are wide` and `design pages fit a phone viewport`,
  both covering the auth flow page.
